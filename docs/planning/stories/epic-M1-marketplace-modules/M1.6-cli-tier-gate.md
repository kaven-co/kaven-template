# M1.6 — CLI: gate de tier antes de `kaven module install`

> **Epic:** M1 | **Agent:** @dev (Bolt)
> **Priority:** P0 — sem isso, qualquer Starter pode instalar módulo Builder e contornar pricing
> **Depends on:** M1.1 (tier definido nos module.json)
> **Blocks:** M1.7 (faz sentido publicar só depois do gate existir)

---

## Contexto

O comando `kaven module install` hoje não verifica se o tier da licença do usuário é
compatível com o tier requerido pelo módulo. Qualquer usuário autenticado pode instalar qualquer
módulo independente do seu plano.

O marketplace retorna `tier` no metadata do módulo. O CLI tem acesso ao JWT em `~/.kaven/auth.json`
que contém o tier do usuário (`tier` field foi adicionado no D1.10).

Esta story adiciona o gate: antes de iniciar download, verifica `module.tier` vs `auth.tier`.

## User Story

**Como** desenvolvedor usando o CLI Kaven,
**Quando** eu tentar instalar um módulo que requer um tier maior que o meu,
**Quero** receber uma mensagem clara explicando qual plano preciso,
**Para que** eu possa decidir fazer upgrade antes de perder tempo.

## Acceptance Criteria

- [ ] `kaven module install {slug}` verifica tier do módulo vs tier do usuário antes de baixar
- [ ] Hierarchy de tiers implementada: `starter < builder < pro < enterprise`
- [ ] Mensagem de erro clara quando tier insuficiente:
  ```
  ✗ Este módulo requer plano Builder ou superior.
    Seu plano atual: Starter
    Upgrade: https://kaven.site/pricing
  ```
- [ ] `kaven marketplace browse` exibe badge de tier em cada módulo (ex: `[Builder]`, `[Pro]`)
- [ ] Módulos inacessíveis no browse aparecem com ícone de lock + tier necessário
- [ ] Módulo `tier: "starter"` é acessível por todos (caso existam módulos gratuitos no futuro)
- [ ] Flag `--skip-tier-check` disponível para uso em testes locais (documentado, não oculto)
- [ ] MSW offline handler atualizado para incluir `tier` no response de `/modules/:slug`
- [ ] Testes: Starter tentando instalar Builder module → erro; Builder instalando Builder module → ok

## tier.utils.ts (lógica core)

```typescript
export const TIER_HIERARCHY = ['starter', 'builder', 'pro', 'enterprise'] as const
export type Tier = typeof TIER_HIERARCHY[number]

export function canInstall(userTier: Tier, moduleTier: Tier): boolean {
  return TIER_HIERARCHY.indexOf(userTier) >= TIER_HIERARCHY.indexOf(moduleTier)
}

export function tierDisplayName(tier: Tier): string {
  return { starter: 'Starter', builder: 'Builder', pro: 'Pro', enterprise: 'Enterprise' }[tier]
}
```

## Notas Técnicas

- O `tier` do usuário vem de `~/.kaven/auth.json` → campo `tier` (adicionado no D1.10)
- O `tier` do módulo vem do response da API do marketplace → `module.tier`
- Se `auth.json` não tem campo `tier` (JWT antigo), assumir `starter` (fail safe)
- Não fazer chamada extra ao servidor para verificar tier — confiar no JWT local (tier offline check)
- Upgrade URL: `https://kaven.site/pricing` (hardcoded por ora, configurável depois)
- O gate é no CLI, não no servidor — o servidor tem seu próprio gate via license validation (v1.1)
- MSW offline handlers (adicionados no C5.1) precisam retornar `tier` nos mocks de módulos
