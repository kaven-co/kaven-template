# M1.4 — Construir módulo `analytics` completo

> **Epic:** M1 | **Agent:** @dev (Bolt)

---

## Contexto

O módulo `analytics` é um shell. O framework tem Attribution Service (EPIC-2.5) que envia para
Meta CAPI e GA4 no backend, mas não tem dashboards de analytics para o próprio SaaS do cliente:
métricas de tenants, MRR, churn, usage por feature, eventos de produto.

Esta story constrói o módulo de analytics de produto (server-side events + dashboards),
distinto do attribution de marketing que já existe no core.

**O que o core já tem (não duplicar):**
- `attribution.service.ts` — Meta CAPI + GA4 para eventos de marketing
- `AuditLog` + `SecurityAuditLog` — logs de segurança/auditoria
- `UsageTracking` (via entitlement service) — quota de features

**O que o módulo adiciona:**
- `AnalyticsEvent` model: eventos de produto (page_view, feature_used, etc.)
- Dashboard de métricas para admin: tenants ativos, MRR estimado, eventos por feature
- PostHog integration (server-side) como provider primário
- Fallback: self-hosted (salvar no próprio DB)

## User Story

**Como** admin do SaaS construído com Kaven,
**Quero** ver métricas de uso do meu produto (tenants ativos, features mais usadas, MRR),
**Para que** eu possa tomar decisões de produto baseadas em dados reais.

## Notas Técnicas

- `posthog-node` é a lib server-side (não `posthog-js` que é browser)
- Dual-write: PostHog como primary, DB como fallback/backup — não depende do PostHog estar configurado
- Sem PII: userId → `sha256(userId + ANALYTICS_SALT)`, nunca email/nome direto
- `GET /analytics/dashboard` é admin-only — verificar `requireRole('admin')`
- Manter compatível com o Attribution Service existente — não conflitar rotas (`/analytics/` vs `/attribution/`)
- Esforço maior (8h) porque tem dashboard frontend com charts — usar Recharts (já no projeto)
